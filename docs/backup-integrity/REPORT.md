# שלב 0 — אמינות גיבוי ושחזור

ענף: `backup-integrity` (מול `claude/personal-tracking-app-4xbd81`). הקשר: PR #27, `docs/ui-audit/REPORT.md` — F09 ו"נקודות שבירות בשכבת הנתונים" D1, D2, D5.

## 1. שינויים בפורמט הגיבוי — שדה אחרי שדה

| שדה | לפני | אחרי | סוג שינוי |
|---|---|---|---|
| `v` | `2` | `2` | ללא שינוי |
| `exported` | ISO 8601 | ISO 8601 | ללא שינוי |
| `weights`, `workouts`, `legacyWorkouts`, `waist`, `checkins`, `standaloneCardio`, `settings`, `customFoods`, `entries`, `targets`, `favorites`, `days`, `creatine`, `quarantine` | כמו שהיו | כמו שהיו, **באותו סדר** | ללא שינוי |
| **`profile`** | לא קיים | **חדש, אופציונלי, תמיד אחרון.** `"default"` (שון / אין פרופיל) או `"partner"`. נכתב בכל ייצוא מהאפליקציה. | הוספה בלבד |
| סריאליזציה | `JSON.stringify(…, null, 2)` | `JSON.stringify(…)` — קומפקטי | אותו תוכן, בלי רווחים |

קובץ **ישן** (בלי `profile`, עם הזחה) נטען בדיוק כמו היום: `parseDb` מחזיר `profile: undefined` = לא ידוע, בלי אזהרה. ערך לא מוכר בשדה (למשל `"someone"`) גם הוא "לא ידוע" ולא דוחה שום רשומה. (`src/lib/schema.ts` — `parseBackupProfile`, `src/lib/exportText.ts` — `BackupProfile`, `buildBackup`.)

## 2. ייבוא — אזהרת פרופיל

`DataScreen.runImport` → `parseDb` → אם `profileConflict(result.profile, PROFILE)` (`src/lib/backup.ts`): באנר שגיאה עם שני הפרופילים, ההסבר (תרגילים משותפים חולקים `id` → ההיסטוריה והצעות המשקל יתערבבו), "ייבא בכל זאת" / "ביטול". **שום דבר לא נכתב לפני האישור**; "ביטול" משאיר את המסד זהה בייט-בייט (נבדק בדפדפן, סעיף 5). חל על מיזוג ועל החלפה; בהחלפה האישור המוקלד ואזהרת התזונה ממשיכים לחול אחריו. קובץ בלי `profile` — אין אזהרה, כמו היום.

## 3. `lastBackup` אחרי ייבוא — מה היה ומה השתנה

**העיקרון:** התזכורת לעולם לא מציגה גיבוי כעדכני יותר ממה שהוא באמת.

| מסלול | לפני | אחרי |
|---|---|---|
| מיזוג (`mergeDb`) | `laterOf(מכשיר, קובץ)` — **המאוחר** גבר. קובץ שיוצא אתמול ממכשיר אחר השתיק את התזכורת במכשיר שלא גובה חודש. (`src/lib/db.ts:132` הישן) | `lastBackupAfterImport(מכשיר, קובץ)` — **המוקדם**, ו-`null` אם אחד מהם `null`. |
| החלפה (`applyReplace`) | `settings` נלקחו מהקובץ כמו שהן — `lastBackup` של הקובץ דרס את המכשיר. | `lastBackup = lastBackupAfterImport(מכשיר, קובץ)`; שאר ההגדרות מהקובץ כמו קודם. |
| דוח הייבוא | לא הזכיר גיבוי. | שורה: "גיבוי אחרון אחרי הייבוא: dd/mm/yyyy" או "אין — ייצא גיבוי חדש של המצב המאוחד". |

למה המוקדם ולא תאריך הקובץ: אחרי מיזוג יש במכשיר רשומות שאף קובץ לא מכיל יחד; אחרי החלפה הקובץ של המכשיר האחר אינו גיבוי של *המכשיר הזה*, והגיבוי האוטומטי שירד לפני ההחלפה הוא של המצב הישן. בשני המקרים הדרך היחידה לאפס את השעון היא ייצוא חדש — וזה בדיוק מה שהתזכורת מבקשת. תופעת לוואי מכוונת: שחזור למכשיר חדש וריק משאיר "גיבוי: אין עדיין" עד הייצוא הראשון.

## 4. תזכורת הגיבוי (F09)

עברה מ-`WeightScreen` ל-`App.tsx`, מעל התוכן של **כל טאב**, בכל פרופיל. שורה אחת (`.notice--row`): "גיבוי: עברו N ימים מהגיבוי האחרון." / "גיבוי: אין עדיין. הנתונים קיימים רק במכשיר הזה." + כפתור "ייצא" שמעביר לטאב נתונים (מוסתר כשכבר שם). לא חוסמת, אותו סף של 7 ימים (`BACKUP_REMINDER_DAYS`), אותו תנאי (יש מה לגבות). בת הזוג, שרואה רק "אימונים" ו"נתונים", מקבלת אותה לראשונה (`reminder-partner-workout-tab.png`).

## 5. ייצוא

- **קומפקטי** — סעיף 1.
- **קובץ, לא רק לוח.** רכיב חדש `components/BackupSave.tsx`: "הורד קובץ גיבוי" (היה בטאב נתונים; **נוסף** לסעיף הייצוא בצ'ק-אין, שהיה לוח בלבד) + "שתף קובץ" דרך Web Share כשהדפדפן תומך בשיתוף קבצים (ב-iOS: גיליון שיתוף → "שמור בקבצים"; `platform/download.ts` — `canShareFile`, `shareTextFile`). ביטול השיתוף אינו נרשם כגיבוי. הלוח נשאר.
- **אימות לפני הודעת ההצלחה.** `verifyBackup(json, db)` (`src/lib/backup.ts`): הטקסט שנכתב לקובץ נקרא חזרה דרך `parseDb` — אותו פרסר של הייבוא — ומספר הרשומות ב-13 המפתחות (כולל אימונים ישנים והסגר) וההגדרות מושווים למסד. רק אימות שעבר מעדכן `lastBackup` ומציג "הקובץ ירד ואומת: N רשומות, כמו במכשיר." כישלון = באנר "הגיבוי לא אומת — אל תסמוך עליו", ו-`lastBackup` לא מתעדכן. חל גם על "העתק JSON מלא" בשני המסכים.

## 7. בדיקות

### יחידה (vitest) — `src/lib/__tests__/backupIntegrity.test.ts`, 20 בדיקות חדשות

- **golden-file**: `fixtures/backup-golden-before.json` יוצא מ-`fixtures/goldenDb.ts` (כל 13 המפתחות מאוכלסים, כולל RIR, החלפה, מקטעי אירובי, צעדים, מתכון, רישום ידני, אימון ישן שלא הומר, הסגר) **בסריאליזציה של הגרסה הקודמת** (`JSON.stringify(buildBackup(db, at), null, 2)`, בלי `profile`). הבדיקות: הקובץ המוקפא הוא הפורמט הישן (16 מפתחות, עם הזחה, בלי `profile`); נטען בגרסה החדשה לאותו מסד בדיוק, אותן ספירות, בלי דחייה חדשה, `profile: undefined`; הייצוא החדש אחרי parse שווה לגולדן פרט ל-`profile`, וסדר המפתחות הקיימים לא זז.
- **round-trip**: מסד → JSON → `parseDb` → JSON: המסד שווה; המחרוזת זהה בייט-בייט מהסבב השני והלאה (הסבב הראשון מנרמל סדר מפתחות של רשומות שנכתבו ביד — באפליקציה כל נתון עובר את הפרסר בטעינה). וגם: ריק ⊕ קובץ = הקובץ (מיזוג לתוך מסד מחוק).
- **קומפקטי**: בלי `\n` ורווחים כפולים, שווה ל-`buildBackup`, קטן ב->25% מההזחה.
- **profile**: בלי ארגומנט — השדה לא נכתב (המבנה של היום); `null → 'default'`, `'partner'`; תמיד אחרון; `parseBackupProfile` לערכים מוכרים/חסר/זבל; `profileConflict` לכל הצירופים; פרופיל שגוי לא דוחה רשומות.
- **lastBackup**: `lastBackupAfterImport` (6 מקרים), `mergeDb` עם קובץ מאוחר/מוקדם/ריק. `db.test.ts` עודכן מ"המאוחר גובר" ל"המוקדם" עם הסבר.
- **verifyBackup**: ייצוא אמיתי עובר (249 רשומות בגולדן — יותר מ-`recordCount`, כי האימות סופר גם יעדים/מועדפים/ימים/הסגר); רשומה שנפלה מתגלה; רשומה שהפרסר ידחה מתגלה (כחוסר + הסגר); הגדרות שונות, גרסה שונה, JSON שבור; מסד ריק → 0 רשומות, תקין.

`npm test`: **52 קבצים, 836 בדיקות עוברות** (היו 816). `npm run build` עובר.

## 8. מה נרשם ולא טופל (מחוץ לשלב הזה, במכוון)

- **`wipeAll`** לא מנקה `fatloss:ui:*` ב-localStorage (D6). לא נגענו.
- **ההסגר** גדל ללא גבול ואין ניקוי חוץ מ"מחק הכול" (D7). לא נגענו.
- **precache** של `moh-foods.json` (1.3MB) נכשל בשקט ב-service worker (F25/D3). לא נגענו ב-SW.
- `fatloss:profile` עדיין **לא משוחזר** בייבוא — בכוונה: הפרופיל נקבע בזמן טעינת המודול, והחלפה דורשת מכשיר ריק. השדה בקובץ משמש לאזהרה בלבד. אם ירצו שחזור אוטומטי במכשיר ריק — שלב נפרד.
